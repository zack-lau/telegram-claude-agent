## BACKGROUND OF THE INVENTION

### Technical Field

The invention addresses the intersection of artificial intelligence document generation, post-quantum cryptography, hardware security modules, and zero-trust cloud storage architectures.

### Technical Problem

Artificial intelligence agents increasingly generate sensitive documents (legal memoranda, medical records, financial analyses) that require multi-decade confidentiality. Current delivery methods expose document content to intermediary service providers, lack protection against future quantum computing attacks ("harvest now, decrypt later"), store decryption keys in software vulnerable to extraction, and provide no cryptographic SDK designed for integration into AI agent runtimes. Existing encrypted delivery solutions either require the service provider to process plaintext, rely exclusively on classical cryptography vulnerable to quantum attacks, or require interactive session establishment between sender and recipient. No existing system provides the combination of AI-agent-native client-side encryption, hybrid post-quantum key encapsulation, hardware-bound recipient keys, and zero-document-storage coordination with delivery to recipient-controlled storage.

### Definitions

As used throughout this application, the following terms have the specified meanings:

- **"Autonomous software agent"** means a software program that performs document generation and encryption operations programmatically without real-time human interaction during the encryption operation, including but not limited to large language model assistants, autonomous coding agents, enterprise AI systems, scheduled automation pipelines, and serverless functions.
- **"User-sovereign cloud storage"** (also "recipient-controlled cloud storage") means cloud storage in which the storage account is owned by and under the sole administrative control of the recipient, not the coordination service or any intermediary, including but not limited to personal Google Drive accounts, OneDrive accounts, and S3 buckets owned by the recipient.
- **"Dual-PRF combiner"** means a key derivation construction that combines two independently-derived pseudorandom keys (one from a classical key agreement, one from a post-quantum key encapsulation) through a cascade of HKDF-Extract operations producing a single combined pseudorandom key, following the extraction-then-expansion pattern of NIST SP 800-56C Rev. 2.
- **"Stateless"** (in the context of this invention) means maintaining no cryptographic session state, key ratchet state, or message sequence state between successive encryption or decryption operations. The system may maintain non-cryptographic operational state such as pinned fingerprints, bundle version history, and revocation cache entries.
- **"Hardware-bound"** means a cryptographic key that is generated within and whose private component never leaves a hardware secure element (e.g., Apple Secure Enclave, Android StrongBox, TEE Keymaster), or in the case of post-quantum keys not natively supported by current secure elements, a key whose private component is stored encrypted under a symmetric wrapping key that is itself derived from a hardware secure element operation.
- **"Cryptographically independent"** (of envelopes) means that the key material, shared secrets, and ephemeral values used to construct one envelope are not derived from, do not depend upon, and do not influence the key material of any other envelope.
- **"Stored data object"** means an encrypted file written to persistent cloud storage for asynchronous retrieval by the recipient, as distinguished from a message transmitted through a real-time or near-real-time messaging relay.

### Description of the Related Art

Artificial intelligence agents are increasingly deployed to generate sensitive documents across legal, medical, financial, and enterprise domains. These documents frequently contain privileged information including legal memoranda, medical diagnoses, financial analyses, trade secrets, and personally identifiable information.

Current delivery methods for AI-generated documents suffer from fundamental security deficiencies:

1. **Plaintext Transmission:** Existing AI agent platforms (including large language model assistants, autonomous coding tools, and enterprise AI systems) transmit generated documents via plaintext email, unencrypted chat interfaces, or standard cloud storage links. The document content is exposed to the AI platform operator, email service providers, and any intermediary network infrastructure.

2. **Server-Side Encryption Limitations:** Existing encrypted delivery solutions perform encryption server-side or require the service provider to possess or process plaintext at some point in the delivery pipeline. The service operator retains technical capability to access document content, creating a single point of compromise.

3. **Absence of Post-Quantum Protection:** Existing encrypted delivery solutions rely exclusively on classical cryptographic algorithms (RSA, ECDH with NIST curves, or X25519) that are vulnerable to quantum computing attacks. Given that sensitive documents such as legal records, medical histories, and financial contracts have multi-decade lifespans, the "harvest now, decrypt later" threat model renders classical-only encryption inadequate for long-lived sensitive documents. Nation-state adversaries are known to intercept and archive encrypted communications for future quantum decryption.

4. **Software-Only Key Storage:** Existing solutions store decryption keys in software keystores or password-derived encryption, lacking hardware binding to dedicated secure elements. Software-stored keys are vulnerable to extraction via malware, operating system compromise, or physical device access.

5. **No AI-Agent-Native Integration:** No existing solution provides a cryptographic SDK designed for integration directly into AI agent runtimes, where encryption occurs entirely within the agent's execution environment before any network transmission.

6. **Service Provider Document Storage:** Existing solutions typically store encrypted documents on the service provider's infrastructure, creating concentration risk and requiring trust in the provider's operational security, data retention policies, and legal jurisdiction.

### Prior Art in Post-Quantum and Hybrid Cryptographic Protocols

The following existing standards and protocols constitute the related art upon which the present invention builds, while differing fundamentally in protocol model, architecture, and application domain:

**Signal PQXDH (Post-Quantum Extended Diffie-Hellman):** The Signal Protocol's PQXDH specification (2023) introduces hybrid post-quantum key agreement for session establishment, combining X25519 ECDH with a CRYSTALS-Kyber KEM. While PQXDH supports asynchronous initial key exchange (the recipient need not be online), it establishes a shared secret for an ongoing communication session with subsequent Double Ratchet key evolution, server-stored message queues, one-time prekeys consumed per session, and post-compromise recovery via ratchet advancement. The present invention differs fundamentally: it creates a self-contained, multi-recipient stored document envelope with no future session key, no server-stored recipient message queue, no one-time prekeys, no ratchet state, and no ongoing communication relationship between sender and recipient. Each envelope is fully independent; the sender need not track any per-recipient state beyond the pinned identity fingerprint and bundle version.

**NIST SP 800-56C Rev. 2 (Two-Step Key Derivation):** NIST Special Publication 800-56C Rev. 2 specifies a two-step extract-then-expand key derivation procedure using HMAC-based constructions. The present invention employs the dual-PRF combiner pattern described therein to combine classical and post-quantum shared secrets, ensuring security as long as at least one component mechanism remains unbroken. SP 800-56C Rev. 2 provides the key derivation framework but does not specify application to multi-recipient document encryption envelopes, AI-agent-native encryption, or hardware-bound key hierarchies.

**HPKE (RFC 9180 — Hybrid Public Key Encryption):** RFC 9180 defines a framework for public key encryption combining a KEM, KDF, and AEAD in a composable manner, including authenticated encryption modes where the sender's identity is bound to the encryption. The present invention draws on HPKE's KEM/KDF/AEAD compositional semantics. However, HPKE does not itself define: a dual classical/post-quantum KEM combiner with transcript hash binding incorporating both parties' long-term identity fingerprints; a multi-recipient CEK-wrapping envelope with per-recipient stanzas; a signed key-bundle hierarchy with rollback protection; an AI-agent delivery flow with coordination service separation; or a zero-document-storage architecture. The present invention provides all of these as an integrated system beyond HPKE's single-recipient, single-KEM framework.

**age Encryption Format:** The age file encryption tool (Filippo Valsorda, 2019) introduces a multi-recipient stanza-based envelope format where a single file key is wrapped independently for each recipient. The present invention adopts age's multi-recipient stanza model for efficient multi-device encryption. However, age uses only classical cryptography (X25519 or scrypt), has no post-quantum component, no hardware secure element integration, no sender authentication, no key hierarchy with signed bundles, and no coordination architecture for AI-agent-to-recipient delivery.

**NIST FIPS 203 (ML-KEM / CRYSTALS-Kyber):** NIST Federal Information Processing Standard 203 (2024) standardizes the Module-Lattice-Based Key-Encapsulation Mechanism (ML-KEM) at three parameter sets. The present invention uses ML-KEM-768 (Security Category 3) as the post-quantum component of its hybrid KEM construction. FIPS 203 defines the KEM primitive only; it does not specify hybrid combination with classical KEMs, multi-recipient envelope formats, key hierarchies, or application-layer protocols.

**COSE/CBOR (RFC 9052 / RFC 8949):** CBOR Object Signing and Encryption (COSE) provides a framework for binary-encoded cryptographic message structures. The present invention uses CBOR encoding for compact envelope serialization and draws on COSE's structural patterns while defining a novel envelope schema specifically designed for hybrid post-quantum multi-recipient document delivery with sender authentication.

**Apple PQ3 Protocol (2024):** Apple's PQ3 protocol for iMessage is a session-based bidirectional messaging protocol with three ratchets (ECDH sender ratchet, Kyber ratchet, and post-compromise ratchet) providing ongoing forward secrecy and post-compromise security within persistent messaging sessions. PQ3 requires continuous session state maintenance, periodic rekeying messages, server-relayed ciphertext, and interactive protocol participation by both parties. As of May 2026, Apple holds no granted USPTO patents covering PQ3's post-quantum cryptographic mechanisms; PQ3 is implemented using NIST-standardized ML-KEM (royalty-free under FIPS 203). The present invention is architecturally distinct: it is a stateless one-shot document delivery envelope with no session state, no ratcheting, no server-relayed ciphertext, no interactive negotiation, and no requirement for ongoing communication between sender and recipient. Where PQ3 optimizes for continuous bidirectional messaging with post-compromise recovery, the present invention optimizes for unidirectional AI-agent-to-recipient document delivery with hardware-bound keys, user-sovereign storage, and zero-document-storage coordination — a fundamentally different protocol model addressing a different threat model and use case.

**Virtru Trusted Data Format (TDF):** Virtru's TDF system performs client-side encryption with multi-recipient key wrapping and delivers encrypted objects to cloud storage. However, TDF requires a Key Access Server (KAS) that mediates every decryption operation — the recipient must contact the KAS and obtain authorization before decrypting each document. The present invention is self-contained: each envelope includes all cryptographic material required for decryption without contacting any server post-delivery. Additionally, TDF uses only classical cryptography, has no post-quantum component, and does not integrate hardware secure element key storage.

**Google Workspace Client-Side Encryption (CSE):** Google CSE enables client-side encryption for Google Drive documents with external key management via an enterprise-controlled Identity Provider (IdP) and external key service. CSE is designed for enterprise administrators controlling encryption policy across an organization. The present invention differs in that: (a) encryption is performed by AI agents rather than human users; (b) key management uses hardware-bound keys in recipient mobile devices rather than enterprise IdP-controlled external key services; (c) the system employs hybrid post-quantum cryptography; and (d) the coordination service never processes ciphertext (Google's infrastructure necessarily stores the encrypted documents).

**Hybrid PQC-KEM Key Establishment Patents (Nix, 2019–2024):** The most closely related granted USPTO patents covering hybrid ECDH + post-quantum KEM constructions are the Nix patent family: US 11,777,719 B2 (IoT and M2M Technologies / Network-1 Technologies, "Public key exchange with authenticated ECDHE and security against quantum computers," priority 2019-03-01), US 12,003,629 B2 (John A. Nix, "Secure server digital signature generation for post-quantum cryptography key encapsulations," priority 2020-12-30), and US 12,388,631 B2 (John A. Nix, "System and methods for secure communication using post-quantum cryptography," priority 2020-09-25). All three patents require interactive multi-message key establishment protocols (TLS-handshake-style 3-message exchanges between server and device), runtime algorithm negotiation between multiple PQC parameter sets, and sequential key derivation producing separate symmetric keys at different protocol stages. The present invention differs in every material aspect: (a) it is a stateless one-shot encryption envelope requiring no interactive exchange or message round-trips; (b) it uses a fixed algorithm suite without runtime negotiation; (c) it combines both ECDH and ML-KEM shared secrets through a single dual-PRF combiner pipeline (not sequential separate KDFs); and (d) it produces a multi-recipient envelope (not a point-to-point channel). The claimed embodiments in the Nix family are materially different from the present invention because they require interactive handshakes and produce point-to-point communication channels, whereas the present invention produces a self-contained multi-recipient stored envelope without any interactive exchange.

Applicant is not presently aware of any granted patent that claims the specific combination of features described in this application. Notably:

- **Dual-PRF combiner with transcript hash binding:** Applicant is not aware of any granted patent claiming this specific key derivation construction (3× HKDF-Extract cascade with document-level transcript hash incorporating both parties' identity fingerprints as HKDF-Expand context).
- **Multi-recipient hybrid post-quantum envelope:** Applicant is not aware of any granted patent claiming the combination of per-recipient KEK-wrapped CEKs with a hybrid classical/post-quantum KEM in a stateless multi-recipient envelope format.

Existing systems for encrypted document delivery generally fall into several categories: (a) bidirectional encrypted messaging protocols with session ratcheting and provider-relayed ciphertext (Signal, PQ3); (b) interactive hybrid PQC key establishment protocols requiring multi-message handshakes (Nix patent family US 11,777,719 / US 12,003,629 / US 12,388,631); (c) server-mediated key access systems where a key access server authorizes each decryption operation (Virtru TDF); (d) client-side encrypted storage systems where the user encrypts files for their own access (Cryptomator, age); and (e) multi-recipient encrypted envelope formats for person-to-person communication (OpenPGP, S/MIME). ## SUMMARY OF THE INVENTION

The present invention provides a system and method for secure delivery of documents generated by artificial intelligence agents, wherein:

(a) **Client-Side Encryption in AI Agent Runtime:** Encryption of document content is performed entirely within the AI agent's execution environment using a cryptographic SDK. The encryption occurs after document generation but before any external transmission from the agent runtime. The invention addresses the secure delivery channel from the agent runtime to the recipient, not the security of the AI generation process itself. The coordination service (hereinafter "Aegis") never receives, processes, or stores plaintext document content.

(b) **Zero-Document-Storage Coordination Architecture:** The Aegis service operates exclusively as a key directory and upload coordinator. It maintains recipient public key bundles and generates delegated upload credentials for the recipient's cloud storage. No document content, plaintext or ciphertext, is stored by the service.

(c) **User-Sovereign Cloud Storage:** Encrypted documents are stored in cloud storage accounts owned and controlled by the recipient (e.g., Google Drive, OneDrive, S3-compatible storage). The recipient maintains full data sovereignty including the ability to revoke access, delete documents, and migrate between providers.

(d) **Hybrid Post-Quantum Key Encapsulation:** A dual key encapsulation mechanism combining classical elliptic curve key agreement (P-256 ECDH per NIST FIPS 186-5) with post-quantum lattice-based key encapsulation (ML-KEM-768 per NIST FIPS 203) ensures security against both current classical attacks and future quantum computing attacks. A dual-PRF combiner construction ensures the combined key material remains secure as long as at least one component mechanism remains unbroken.

(e) **Hardware-Bound Decryption Keys:** Classical private keys (P-256 ECDH and P-256 ECDSA) are generated and stored within mobile device hardware secure elements (Apple Secure Enclave on iOS, Android StrongBox or TEE Keymaster on Android). These keys never leave the secure element hardware boundary. Post-quantum private keys (ML-KEM-768) are stored encrypted, wrapped by symmetric keys derived from hardware secure element operations.

(f) **Multi-Recipient Encryption:** A single document is efficiently encrypted to multiple recipient devices using a random Content Encryption Key (CEK) that is independently wrapped for each recipient using per-recipient Key Encryption Keys (KEKs) derived from the hybrid key encapsulation mechanism.

(g) **Sender Authentication:** ECDSA-P256 digital signatures computed by the sending AI agent provide cryptographic proof of document origin, enabling tiered sender verification policies (open mode with unknown-sender warnings, strict mode with authorized-sender-only enforcement).

## DETAILED DESCRIPTION OF THE INVENTION

### 1. System Architecture Overview

The invention comprises four principal components operating in coordination:

**Component A — AI Agent with Client-Side Encryption SDK:** An artificial intelligence agent (such as a large language model assistant, autonomous coding agent, or enterprise AI system) equipped with a cryptographic SDK that performs all encryption operations locally within the agent's runtime environment. The SDK communicates with the coordination service only for public key retrieval and upload credential generation. The SDK is preferably implemented as a single compiled native library (e.g., Rust crate exposing a C ABI) to ensure memory safety and enable cross-platform deployment.

**Component B — Coordination Service (Key Directory and Upload Coordinator):** A cloud service that maintains a directory of recipient public key bundles and generates delegated upload credentials (pre-signed URLs or short-lived OAuth tokens) enabling AI agents to write encrypted documents directly to recipients' cloud storage. The coordination service explicitly does not receive, process, store, or have access to plaintext document content, Content Encryption Keys, Key Encryption Keys, or any private key material.

**Component C — User-Sovereign Cloud Storage:** Cloud storage accounts owned by recipients (e.g., Google Drive with `drive.file` OAuth scope) where encrypted document envelopes are stored. The recipient grants the coordination service a scoped OAuth refresh token during onboarding, enabling scoped write access to an application-specific folder. The cloud storage provider sees only encrypted ciphertext.

**Component D — Mobile Decryption Application with Hardware-Bound Keys:** A mobile application (iOS and Android) that generates and manages cryptographic key pairs within the device's hardware secure element, publishes signed public key bundles to the coordination service, retrieves encrypted envelopes from the recipient's cloud storage, and performs decryption using hardware-bound keys. The application enforces biometric authentication before key access.

### 2. Cryptographic Key Hierarchy

The invention employs a three-level key hierarchy separating long-lived identity from rotatable operational keys:

**Level 1 — Account Identity Key (AIK):** A P-256 ECDSA key pair generated at account creation within the device's hardware secure element (Apple Secure Enclave or Android StrongBox). The AIK is long-lived and never rotates under normal operation. The public key fingerprint (truncated SHA-256 of the public key, encoded as 16 Crockford Base32 characters in groups of four, providing 80 bits of preimage resistance) serves as the stable identifier for the account across all device key rotations. The AIK signs all device key bundles, establishing a chain of trust from the stable identity to rotatable operational keys.

**Level 2 — Device Encryption Keys:** Per-device key pairs comprising a P-256 ECDH key pair (for classical key exchange, stored in hardware secure element) and an ML-KEM-768 key pair (for post-quantum key encapsulation, stored encrypted in software wrapped by a hardware-derived symmetric key). Device encryption keys are rotated every 90 days. Each device key pair is individually signed by the Account Identity Key.

**Level 3 — Device Signing Keys:** Per-device P-256 ECDSA key pairs (stored in hardware secure element) used for signing revocation tokens and device-origin assertions. Signed by the Account Identity Key. Rotated on the same 90-day schedule as device encryption keys.

### 3. Signed Key Bundle with Rollback Protection

Recipient public keys are distributed as signed bundles with the following structure:

```
signed_key_bundle = {
  account_identity_pubkey: P-256 point (65 bytes uncompressed),
  devices: [
    {
      device_id: string,
      ecdh_pubkey: P-256 point (65 bytes),
      ecdsa_pubkey: P-256 point (65 bytes),
      mlkem_pubkey: ML-KEM-768 public key (1184 bytes),
      created: Unix timestamp,
      signed_by_identity: ECDSA-P256 signature from AIK
    }, ...
  ],
  bundle_version: unsigned integer (monotonically increasing),
  bundle_expiry: Unix timestamp (bundle signing time + 7 days),
  bundle_signature: ECDSA-P256 signature from AIK (covers all above fields)
}
```

**Rollback Protection Mechanism:** Sending agents store a tuple `(recipient_id, last_seen_bundle_version, last_seen_bundle_hash)` for each recipient. Upon fetching a key bundle, the agent verifies: (a) `bundle_signature` validates against the pinned Account Identity Key fingerprint; (b) each device entry's `signed_by_identity` validates against the same AIK; (c) `bundle_version >= last_seen_bundle_version`; (d) `bundle_expiry` is in the future; and (e) when `bundle_version == last_seen_bundle_version`, the SHA-256 hash of the canonical CBOR encoding of the bundle matches the cached `last_seen_bundle_hash`. Any verification failure causes the SDK to refuse encryption and alert the operator.

### 4. Hybrid Post-Quantum Key Encapsulation Mechanism

The invention employs a hybrid key encapsulation combining P-256 ECDH (classical, NIST FIPS 186-5) and ML-KEM-768 (post-quantum, NIST FIPS 203) via a dual-PRF combiner construction following the extraction-then-expansion key derivation pattern described in NIST SP 800-56C Rev. 2:

**Step 1 — Classical Key Agreement:** The sender generates an ephemeral P-256 key pair and performs ECDH key agreement against the recipient's device P-256 ECDH public key, producing `ecdh_shared_secret`.

**Step 2 — Post-Quantum Key Encapsulation:** The sender performs ML-KEM-768 encapsulation against the recipient's ML-KEM-768 public key, producing `mlkem_shared_secret` and `mlkem_ciphertext`.

**Step 3 — Dual-PRF Combiner Construction:**
```
prk_ecdh = HKDF-Extract(salt=suite_id, ikm=ecdh_shared_secret)
prk_mlkem = HKDF-Extract(salt=suite_id, ikm=mlkem_shared_secret)
prk = HKDF-Extract(salt=prk_ecdh, ikm=prk_mlkem)
KEK = HKDF-Expand(prk, info=context_string, L=32)
```

Where:
- `suite_id` = `"Aegis-P256-ECDH-ML-KEM-768-HKDF-SHA256-AES256GCM"` (algorithm identifier string)
- `context_string` = `"aegis-v1" || suite_id || recipient_id || transcript_hash`
- `transcript_hash` = `SHA-256(envelope_version || suite_id || sender_signing_key_fingerprint || recipient_account_identity_fingerprint || recipient_ecdh_pubkey || recipient_mlkem_pubkey || ecdh_ephemeral_pubkey || mlkem_ciphertext)`

**Transcript Hash Binding:** The key derivation is cryptographically bound to the full key exchange transcript including algorithm identifiers, both parties' identities, all public keys involved, the envelope version, and the ML-KEM ciphertext. This binding prevents cross-session key reuse, identity misbinding attacks, and algorithm downgrade attacks.

**Security Property:** Following the dual-PRF combiner pattern (as formalized by Bindel, Brendel, Fischlin, Goncalves, and Stebila, "Hybrid Key Encapsulation Mechanisms and Authenticated Key Exchange," 2019; and Giacon, Heuer, Poettering, "KEM Combiners," 2018), the combined Key Encryption Key (KEK) remains computationally indistinguishable from random as long as at least one component KEM (P-256 ECDH or ML-KEM-768) remains unbroken. The cascade construction — where the output of one HKDF-Extract serves as the salt for the next — is the correct realization of the dual-PRF combiner property: in the HMAC key position (salt), a pseudorandom `prk_ecdh` ensures output security if ECDH is unbroken; in the HMAC message position (IKM), a pseudorandom `prk_mlkem` ensures output security if ML-KEM is unbroken. This is strictly stronger than concatenating both shared secrets into a single HKDF-Extract call, which would lose the independent dual-PRF guarantee. The HKDF-Extract operation in step 3 takes two pseudorandom keys and produces a single pseudorandom key of correct length (32 bytes for SHA-256), consistent with RFC 5869 §3.1 which specifies salt should be "a random (or pseudorandom) string of the length HashLen."

### 5. Multi-Recipient Encryption — Canonical Envelope Construction

The invention specifies a canonical construction ordering for creating encrypted document envelopes:

**Step 1 — Generate Content Encryption Key (CEK):** Generate one random 32-byte symmetric key from the platform's cryptographically secure pseudorandom number generator (CSPRNG). The CEK is independent of any KEM-derived material.

**Step 2 — Build Recipient Stanzas:** For each recipient device:
- (a) Perform P-256 ECDH key agreement with a fresh ephemeral key pair against the recipient device's ECDH public key;
- (b) Perform ML-KEM-768 encapsulation against the recipient device's ML-KEM public key;
- (c) Derive the per-recipient KEK via the dual-PRF combiner (Section 4);
- (d) Wrap the CEK: `wrapped_cek = AES-256-KWP(KEK, CEK)` per RFC 5649.

**Step 3 — Assemble Unsigned Header:** Construct the complete binary-encoded header with all fields populated except `sender.signature` which is set to `null`. The header includes: envelope version, algorithm identifiers, recipient stanzas (from Step 2), sender identifier (signing key fingerprint), and metadata (document ID, creation timestamp, and optionally a provenance object comprising agent ID, runtime version, session ID, and model ID).

**Step 4 — Compute Header Hash:** `header_hash = SHA-256(canonical_encoding(unsigned_header))` where `unsigned_header` is the header with `sender.signature = null`.

**Step 5 — Encrypt Payload:** `AES-256-GCM(key=CEK, nonce=random_12_bytes, plaintext=document, aad=header_hash)` producing a single ciphertext blob shared by all recipients. The header hash serves as Additional Authenticated Data (AAD), cryptographically binding the payload to the header without requiring a separate MAC.

**Step 6 — Compute Sender Signature:** `sender_signature = ECDSA-P256(agent_signing_key, "aegis-v1-sender-sig" || header_hash || SHA-256(nonce || ciphertext))`. The signature is encoded in raw fixed-width r||s format (64 bytes for P-256). The signature covers a domain-separated concatenation of the header hash and the payload hash, providing sender authentication over the entire envelope. The preferred embodiment uses deterministic ECDSA nonce generation per RFC 6979 to eliminate dependence on entropy source quality during signing; however, implementations MAY use randomized ECDSA with a cryptographically secure random number generator.

**Step 7 — Finalize Envelope:** Insert `sender_signature` into the header's `sender.signature` field. The final envelope comprises the complete header (with signature populated) and the encrypted payload (nonce concatenated with ciphertext).

**Construction Order Rationale:** Recipient stanzas must be constructed before payload encryption because the unsigned header (containing recipient stanzas) is used as AAD for the AEAD. The sender signature must be computed after encryption because it covers both the header hash and the payload hash, neither of which can exist at the time the header hash is computed.

### 6. Aegis Envelope v1 Data Format

The encrypted document envelope is encoded as follows:

```
Aegis Envelope v1
+-- Header (binary-encoded, preferably CBOR per RFC 8949)
|   +-- version: unsigned integer (1)
|   +-- algorithms: {
|   |     kem: "P256-ECDH+ML-KEM-768",
|   |     kdf: "HKDF-SHA256",
|   |     aead: "AES-256-GCM"
|   |   }
|   +-- sender: {
|   |     id: sender_signing_key_fingerprint (16 chars),
|   |     pubkey: P-256 point (65 bytes uncompressed, self-declared sender public key),
|   |     signature: ECDSA-P256 signature (64 bytes, raw fixed-width r||s)
|   |   }
|   +-- recipients: [
|   |     {
|   |       id: recipient_key_fingerprint,
|   |       type: "device" | "recovery" | "hardware-key",
|   |       ecdh_ephemeral: P-256 point (65 bytes uncompressed),
|   |       mlkem_ciphertext: ML-KEM-768 ciphertext (1088 bytes),
|   |       wrapped_cek: AES-256-KWP wrapped CEK (40 bytes)
|   |     }, ...
|   |   ]
|   +-- metadata: {
|         created: Unix timestamp,
|         doc_id: UUID v4,
|         provenance: {  // optional
|           agent_id: string,
|           runtime_version: string,
|           session_id: string,
|           model_id: string
|         }
|       }
+-- Payload
    +-- nonce: 12 bytes (random)
    +-- ciphertext: AES-256-GCM output
```

The envelope format draws on semantics from HPKE (RFC 9180), age-style multi-recipient stanzas, and COSE binary encoding (RFC 9052), while constituting a novel combination adapted for the specific requirements of AI-agent-to-mobile-recipient encrypted delivery with hybrid post-quantum key encapsulation.

### 7. Zero-Document-Storage Coordination Architecture

The coordination service architecture is defined by a strict separation between coordination metadata and document content:

**Data that flows through the coordination service:**
- Public key bundle lookups (signed bundles served from key directory)
- Upload coordination metadata (recipient storage endpoint, folder path, pre-signed URL generation)
- API authentication and rate limiting
- Audit log entries (agent ID, recipient ID, timestamp, operation outcome)
- Revocation status queries

**Data that NEVER flows through the coordination service:**
- Plaintext document content
- Private keys (ECDH, ECDSA, or ML-KEM)
- Content Encryption Keys (CEKs)
- Key Encryption Keys (KEKs)
- Decrypted data of any kind
- Encrypted document ciphertext (uploaded directly to recipient's storage)

### 8. Upload Coordination via Delegated OAuth

The invention coordinates uploads to recipient cloud storage using delegated OAuth:

(a) During onboarding, the recipient authorizes the coordination service with a scoped OAuth refresh token (e.g., Google Drive `drive.file` scope) granting scoped access limited to an application-specific folder.

(b) When an AI agent requires an upload endpoint, the coordination service uses the stored refresh token to generate a pre-signed upload URL or short-lived access token scoped to the recipient's Aegis folder.

(c) The AI agent uploads the encrypted envelope directly to the recipient's cloud storage using the provided credentials, without the ciphertext transiting through the coordination service.

(d) The OAuth token stored by the coordination service is encrypted at rest using AES-256-GCM with keys managed by a cloud key management service (e.g., AWS KMS).

### 9. Hardware-Bound Key Storage

**Tier 1 — Mobile Device Secure Element (Default):**
- iOS: Apple Secure Enclave stores Account Identity Key, Device ECDH key, and Device ECDSA key (all P-256). Keys are generated within and never leave the Secure Enclave.
- Android: StrongBox Keymaster (preferred) or TEE Keymaster (fallback) stores identical P-256 key material.
- ML-KEM-768 private key: Encrypted at rest using a symmetric key derived from a hardware secure element P-256 ECDH key agreement operation against a device-local ephemeral point. Decrypted into memory only for the duration of decapsulation, then immediately wiped via platform-native secure zeroing (`memset_s` or equivalent).
- The application verifies `isInsideSecureHardware()` at key generation and refuses to generate keys on devices lacking hardware-backed keystore support.

**Tier 2 — External Hardware Keys (Optional):**
- NFC-connected hardware security keys (e.g., YubiKey 5 NFC, Nitrokey) or USB-connected keys for users requiring physical key separation from the mobile device.
- The application verifies the hardware key's certificate chain (manufacturer CA to device certificate) before performing cryptographic operations.

**Tier 3 — Enterprise Cloud Key Management:**
- AWS KMS for key backup wrapping.
- AWS Nitro Enclaves for attestation-verified server-assisted decryption in enterprise deployments.
- AWS KMS External Key Store (XKS) for "bring your own HSM" enterprise customers.

### 10. Sender Authentication and Authorized Sender Policies

Each sending AI agent possesses a P-256 ECDSA signing key pair. The sender signature in the envelope header enables tiered sender verification:

**Open Mode (default):** The sender's signature is verified against the public key included in the envelope's sender field (self-declared key). The signature proves the sender controls the corresponding private key, even if the key is not pre-registered with the recipient. Unknown senders (signing keys not in the recipient's authorized list) trigger a warning banner in the decryption application. The envelope remains decryptable. The recipient may inspect the sender key fingerprint and choose to trust or block.

**Strict Mode (enterprise):** The sender's signature is verified against a pre-registered public key in the recipient's authorized sender list. Only envelopes from senders whose signing keys appear in the authorized list are decrypted. Envelopes from unknown senders are rejected without decryption. The recipient maintains the authorized sender list signed by their Account Identity Key.

### 11. Key Revocation Mechanism

Device key revocation employs signed revocation tokens with timestamp service counter-signatures:

(a) When a device is decommissioned, a signed revocation token is published. The token is signed by the device's own ECDSA signing key (proving ownership) or by a designated administrator key (for lost/stolen devices).

(b) Revocation tokens are counter-signed by the coordination service's timestamp service, producing a verifiable statement: "device X was revoked at time T."

(c) Before encrypting to any device key, the sending agent checks both cloud storage revocation records and the timestamp service revocation endpoint.

(d) **Fail-Closed Cache Policy:** Agents cache revocation check results with a configurable TTL (default: 1 hour). If either revocation source is unreachable and the cache is past TTL, the agent MUST NOT encrypt (fail-closed, no exceptions). There is no grace period or circuit breaker.

### 12. Deduplication via Cryptographically Unique Document Identifiers

Each encrypted envelope contains a UUID v4 `doc_id` generated at encryption time and a `created` timestamp. The recipient application maintains a local database of previously verified document identifiers. The deduplication mechanism enforces authentication-before-insertion ordering: a `doc_id` is inserted into the seen set only after both sender signature verification and payload AEAD authentication succeed. This prevents deduplication denial-of-service attacks where an attacker sends invalid envelopes with legitimate document identifiers to block real deliveries.

### 13. Agent-Side Fingerprint Verification (Trust-on-First-Use)

The invention employs a Trust-on-First-Use (TOFU) model for agent-side key verification:

(a) At account creation, the mobile application displays the recipient's fingerprint derived from the Account Identity Key (16 Crockford Base32 characters in groups of four, e.g., `ABCD-EF12-3456-7890`, providing 80 bits of preimage resistance via 16 characters × 5 bits per character).

(b) The human operator provides this fingerprint to the AI agent during initial configuration.

(c) The agent SDK stores the fingerprint as a pinned value along with initial bundle version and hash state.

(d) On subsequent operations, the SDK verifies fetched key bundles against the pinned fingerprint. Any mismatch (indicating potential key substitution attack) causes encryption refusal and operator alerting.

(e) Since the fingerprint derives from the long-lived Account Identity Key rather than rotatable device keys, it remains stable across routine device key rotations.

### 14. P-256 Public Key Validation Requirements

All P-256 public keys are validated before use in ECDH key agreement operations:
- Curve membership verification (point satisfies P-256 curve equation)
- Point-at-infinity rejection
- Coordinate range verification (within [0, p-1])
- Format normalization (compressed and uncompressed accepted, normalized internally)

### 15. Memory Safety for Cryptographic Material

The invention specifies memory safety requirements for all sensitive cryptographic material:
- All cryptographic operations handling key material are performed in platform-native code (or Rust via FFI) with explicit secure zeroing after use
- Raw key bytes never transit through garbage-collected language runtime objects
- ML-KEM private keys are decrypted from hardware-wrapped form only for decapsulation duration, then immediately wiped
- A single Rust crate (`aegis-crypto`) implementing all cryptographic operations and exposing a C ABI is the preferred implementation, enabling a single auditable codebase with Rust's ownership model preventing use-after-free and buffer overflow vulnerabilities

### 16. Streaming and Chunked Encryption for Large Documents

For documents exceeding a configurable size threshold (default: 4 mebibytes), the invention provides a streaming encryption mode using a two-phase construction that avoids circularity between header hashes and chunk encryption:

**Phase 1 — Streaming Header and Chunk Encryption:**

(a) The document payload is divided into fixed-size chunks (default: 64 kibibytes) with a final variable-length chunk.

(b) A streaming header is assembled containing: envelope version, algorithm identifiers, recipient stanzas (with wrapped CEKs), sender identification, metadata, and streaming mode indicators — but explicitly excluding any chunk hashes. A streaming header hash is computed as `SHA-256(canonical_encoding(streaming_header))`.

(c) Each chunk is individually encrypted using authenticated encryption with associated data (AEAD), with the streaming header hash as AAD and a per-chunk nonce derived deterministically via `chunk_nonce = HKDF-Expand(CEK, info="aegis-chunk-nonce" || uint64_be(chunk_index), L=12)`, producing a unique 12-byte nonce per chunk. This deterministic derivation follows the STREAM construction pattern (analogous to TLS 1.3 record layer nonce derivation per RFC 8446 §5.3), preventing chunk reordering or duplication attacks and eliminating dependence on per-chunk random nonce generation.

**Phase 2 — Chunk Manifest Construction:**

(d) After all chunks are encrypted, a chunk manifest is constructed containing: the total number of chunks, the SHA-256 hash of each chunk's ciphertext, the chunk size, and the total document size.

(e) The manifest is signed by the sender's digital signature key: `manifest_signature = ECDSA-P256(agent_signing_key, "aegis-v1-chunk-manifest" || streaming_header_hash || SHA-256(canonical_encoding(manifest)))`.

(f) The signed chunk manifest is appended to the envelope as a separate section following the payload chunks, not included in the streaming header.

(g) The recipient verifies each chunk against the manifest during streaming decryption, enabling incremental processing of large documents without buffering the entire ciphertext in memory.

### 17. Privacy-Preserving Audit Logs

The coordination service maintains privacy-preserving audit logs that record delivery metadata without exposing document content:

(a) Each audit log entry comprises: sender agent identifier, recipient account identifier, timestamp, operation type (key fetch, credential generation, upload confirmation), and operation outcome (success or categorized failure code).

(b) No document content, document identifiers, file names, file sizes, or content types are recorded in audit logs.

(c) Audit log entries are retained for a configurable period (default: 90 days) and are cryptographically chained using hash-linking (each entry includes the SHA-256 hash of the previous entry) to provide tamper evidence.

(d) Recipients may request audit log extracts pertaining to their account, enabling detection of unauthorized delivery attempts without revealing document contents.

### 18. Transparency Log for Key Directory

The coordination service maintains an append-only transparency log for key bundle operations:

(a) Every key bundle publication, update, and revocation is recorded as a signed, sequentially numbered entry in an append-only log.

(b) Sending agents may audit the transparency log to verify that the key bundle they received is consistent with the log entry, detecting equivocation attacks where the coordination service presents different bundles to different senders.

(c) The log supports inclusion proofs (proving a specific bundle version exists in the log) and consistency proofs (proving the log has not been retroactively modified).

(d) Log entries are signed by the coordination service and counter-signed by independent witnesses on a configurable schedule, providing split-trust verification.

### Independent Claim 40 — Dual-PRF Combiner Construction

**Claim 40.** A method for deriving a cryptographic key from a hybrid key encapsulation combining a classical key agreement and a post-quantum key encapsulation mechanism, the method comprising:

- (b) performing a lattice-based post-quantum key encapsulation to obtain a post-quantum shared secret and a post-quantum ciphertext;
- (c) computing a first pseudorandom key by applying HKDF-Extract with a suite identifier as salt and the classical shared secret as input keying material;
- (d) computing a second pseudorandom key by applying HKDF-Extract with the suite identifier as salt and the post-quantum shared secret as input keying material;
- (e) computing a combined pseudorandom key by applying HKDF-Extract with the first pseudorandom key as salt and the second pseudorandom key as input keying material;
- (f) computing a document-level transcript hash comprising a cryptographic digest of data including at least: a sender identity fingerprint, a recipient identity fingerprint, an ephemeral public key from step (a), and the post-quantum ciphertext from step (b); and
- (g) deriving an output key by applying HKDF-Expand to the combined pseudorandom key with a context string incorporating the document-level transcript hash;
wherein the output key is cryptographically bound to both parties' long-term identities and all ephemeral key exchange material, preventing cross-use key reuse and identity misbinding; and wherein the method is performed independently for each recipient without chaining or state dependency between recipients.

## ABSTRACT

A system and method for secure delivery of documents generated by artificial intelligence agents to recipients using hybrid post-quantum cryptography and hardware-bound keys. The system comprises an AI agent with a client-side encryption SDK that performs all cryptographic operations within the agent's runtime, a coordination service operating solely as a key directory and upload coordinator that never processes plaintext or ciphertext, user-sovereign cloud storage where encrypted envelopes are stored in accounts owned by recipients, and a mobile decryption application utilizing hardware secure elements for key storage. Encryption employs a hybrid key encapsulation mechanism combining classical elliptic curve key agreement with a lattice-based post-quantum key encapsulation mechanism via a dual-PRF combiner following the extraction-then-expansion key derivation pattern described in NIST SP 800-56C Rev. 2, providing security against both classical and quantum attacks. A canonical envelope construction ordering with digital signature sender authentication, monotonically versioned signed key bundles with rollback protection, fail-closed revocation caching, hardware-wrapped post-quantum key lifecycle management, and streaming chunked encryption provide comprehensive security guarantees while maintaining zero-document-storage architecture.
